# Deployment — Render (API + database) and Vercel (frontend)

The app is two deployables:

| Piece | Host | Why |
|---|---|---|
| `backend/` Express API | **Render** | needs a long-lived process |
| PostgreSQL | **Neon** | serverless Postgres, no 30-day expiry |
| `frontend/` React SPA | **Vercel** | static build, served from the edge |

Deploy Render first — the frontend needs the API's URL before it can be built.

---

## Part 1 — Render

### 1. Create the blueprint

The repo ships [`render.yaml`](../render.yaml), which declares both the database and the API.

1. Go to <https://dashboard.render.com> and sign in with GitHub.
2. **New → Blueprint**.
3. Pick `GauravSoni-SNS/PATENT_DATA_MANAGEMENT-TOOL`, branch `main`.
4. Render reads `render.yaml` and shows two resources: `lexpatent-db` (Postgres) and `lexpatent-api` (web service). Approve.

It will ask for the one value marked `sync: false`:

- **`FRONTEND_URL`** — you don't have the Vercel domain yet. Put `http://localhost:5173` for now and correct it in Part 3.

`JWT_SECRET` and `JWT_REFRESH_SECRET` are generated by Render (`generateValue: true`), so no secret ever lives in the repo.

### 2. What the build does

```
rootDir:       backend
buildCommand:  npm ci && npm run render:build
startCommand:  npm run start:prod
healthCheck:   /api/v1/health
```

`render:build` only compiles TypeScript. The schema push runs in the **start** command instead, because `DATABASE_URL` is not present in Render build environments - see troubleshooting below. `postinstall` runs `prisma generate` so the client matches the schema.

`prisma db push` is idempotent: on later restarts it finds no drift and exits in a second or two.

```
https://lexpatent-api.onrender.com
```

Check it:

```bash
curl https://lexpatent-api.onrender.com/api/v1/health
```

Expect `{"status":"ok","timestamp":"..."}`.

### 3. Seed the demo data

The database starts empty — logging in will fail until it is seeded. In the Render dashboard open the **`lexpatent-api` service → Shell** and run:

```bash
npm run db:seed
```

That creates the firm, the users, the clients and the six demo matters. Verify:

```bash
curl -X POST https://lexpatent-api.onrender.com/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"s.jenkins@lexpatent-ip.com","password":"password123"}'
```

A JSON body with `accessToken` means the API and database are live.

> **Change the seeded passwords before anyone else has the URL.** The seed ships `password123` for every account.

## Part 2 — Vercel

1. <https://vercel.com/new> → import the same repo.
2. **Root Directory: `frontend`** (this is the setting people miss — without it the build fails).
3. Framework preset: Vite. Build `npm run build`, output `dist`. Vercel detects both.
4. Environment variable:

   | Name | Value |
   |---|---|
   | `VITE_API_URL` | `https://lexpatent-api.onrender.com/api/v1` |

   Note the `/api/v1` suffix — the client appends paths directly to it.
5. Deploy. You get `https://<project>.vercel.app`.

`VITE_*` values are baked in at build time, so changing it later needs a redeploy, not just a restart.

---

## Part 3 — Point the API back at the frontend

The API only accepts browser requests from origins in `FRONTEND_URL`.

In Render → `lexpatent-api` → **Environment**, set:

```
FRONTEND_URL=https://<project>.vercel.app
```

A comma-separated list is supported, which is how you allow preview deploys:

```
FRONTEND_URL=https://lexpatent.vercel.app,https://lexpatent-git-staging-you.vercel.app
```

Save — Render restarts the service. Then load the Vercel URL and log in. If login succeeds and the Board fills with matters, both halves are talking.

## Known limits of this setup

**Render free tier sleeps.** After 15 minutes idle the service suspends; the next request takes ~50 seconds to wake it. The first login after a quiet period will look broken but isn't. The Starter plan removes this.

**Uploaded receipts do not survive a deploy.** `UPLOAD_DIR` is on the container's ephemeral disk, so receipt files are lost on every restart or redeploy (database rows survive; the files do not). Two fixes: attach a Render **persistent disk** and point `UPLOAD_DIR` at its mount path, or move uploads to object storage (S3/R2).

**The simulated-clock control is global.** `SIMULATED_DATE` is process state, so changing it in the UI changes it for everyone hitting that instance, and it resets on restart. Fine for a demo, wrong for production — real deployments should drop the simulate control.

**Free Postgres expires.** Render's free database is removed after 30 days. Back up or upgrade before then.

## Before this faces real clients

1. `PATCH /matters/:id` passes `req.body` straight to `prisma.matter.update`, so any authenticated user can write any column — `firmId` included, which moves a matter into another firm. Needs a zod whitelist.
2. Rotate the seeded `password123` accounts.
3. No rate limiting on `/auth/login`.
4. `GET /uploads/*` is served without auth — anyone with a URL can read a receipt.

## Troubleshooting

### Build fails: `Environment variable not found: DATABASE_URL` (P1012)

```
> prisma db push --skip-generate
Error code: P1012
error: Environment variable not found: DATABASE_URL.
```

Render build environments do not receive the database connection string — a
`fromDatabase` reference resolves at runtime, not at build. Any Prisma command
that opens a connection therefore fails during the build.

Fixed by moving the schema push out of `buildCommand` into `startCommand`:

```yaml
buildCommand: npm ci && npm run render:build   # tsc only
startCommand: npm run start:prod               # prisma db push, then node dist/index.js
```

If you created the service by hand rather than from the blueprint, set both
commands on the service's **Settings** page to match, and confirm `DATABASE_URL`
is listed under **Environment** (it appears automatically only when the service
and database were created together by the blueprint; otherwise add it yourself
using the database's **Internal Database URL**).

### Build fails: `Could not find a declaration file for module 'express'` / `Cannot find name 'fs'`

```
error TS7016: Could not find a declaration file for module 'express'.
error TS2591: Cannot find name 'fs'. Do you need to install type definitions for node?
```

`NODE_ENV=production` is set on the service, and npm honours it by omitting
`devDependencies` — which is where `typescript` and every `@types/*` package
lives. The compiler then runs without any type declarations.

Fixed by installing dev dependencies explicitly:

```yaml
buildCommand: npm ci && npm run render:build
```

Fixed by moving everything the deploy needs into dependencies: typescript, prisma and the @types packages, so the build works under any install command. prisma must be a real dependency regardless, because the start command runs prisma db push and needs the CLI at runtime.

### Using Neon instead of Render Postgres

`render.yaml` no longer declares a database; `DATABASE_URL` is `sync: false`
and set by hand to a Neon connection string.

Use Neon's **direct** connection, not the pooled one. Neon hands out two hosts:

```
ep-xxxx-pooler.region.aws.neon.tech    <- pooled (PgBouncer)
ep-xxxx.region.aws.neon.tech           <- direct
```

Take the direct host — drop `-pooler` from the hostname. Two reasons:

1. `prisma db push` issues DDL, which is unreliable through a transaction
   pooler.
2. This is one long-lived Node process with Prisma's own connection pool, so
   PgBouncer buys nothing. Pooling matters for serverless functions, which this
   is not.

Trim the query string to `?sslmode=require`. Neon's console appends
`&channel_binding=require`, which is a libpq option that Prisma's driver does
not accept.

Final shape:

```
postgresql://USER:PASSWORD@ep-xxxx.region.aws.neon.tech/neondb?sslmode=require
```

If you later move the API to serverless, switch `url` to the pooled host and add
`directUrl` (pointing at the direct host) to the datasource block in
`schema.prisma` so migrations keep working.

### Live login says "Invalid email or password"

The database has tables but no rows. `prisma db push` creates the schema; it
does not seed. Until the seed runs, no user exists and every login is a
genuine 401.

**Render's Shell tab requires a paid instance type**, so on the free plan seed
from your own machine against the same database:

```bash
cd backend
DATABASE_URL="<your Neon direct URL>" npm run db:seed:remote
```

PowerShell:

```powershell
cd backend
$env:DATABASE_URL="<your Neon direct URL>"; npm run db:seed:remote
```

**The seed is destructive.** It runs `deleteMany()` across every table before
inserting, so never point it at a database that already holds real matters.

Confirm it worked without a browser:

```bash
curl -X POST https://<your-api>.onrender.com/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"s.jenkins@lexpatent-ip.com","password":"password123"}'
```

`accessToken` in the response means the database is seeded and the API is
healthy — any remaining browser-side failure is then CORS or `VITE_API_URL`.

## Alert channels: email and WhatsApp

Alerts are generated by `POST /api/v1/notifications/scan` and delivered over
every configured channel. Nothing is faked: a notification is only recorded as
`SENT`/`DELIVERED` when a channel actually accepted it, and each attempt is
stored per recipient in `notifications.deliveries`.

| Status | Meaning |
|---|---|
| `DELIVERED` | every attempt succeeded |
| `SENT` | at least one succeeded, at least one failed |
| `FAILED` | every attempt failed |
| `PENDING` | nothing was dispatched — usually no channel is configured |

### Email (SMTP)

| Variable | Example |
|---|---|
| `SMTP_HOST` | `smtp.gmail.com` |
| `SMTP_PORT` | `587` (STARTTLS) or `465` (implicit TLS) |
| `SMTP_USER` | mailbox login |
| `SMTP_PASS` | app password, never the account password |
| `SMTP_FROM` | `LexPatent Docket Radar <docket@yourfirm.com>` |

Gmail and Outlook both require an app password with 2FA enabled; a normal
password is rejected.

### WhatsApp (Visity)

| Variable | Purpose |
|---|---|
| `WHATSAPP_API_URL` | the send endpoint from your Visity dashboard |
| `WHATSAPP_API_KEY` | API token |
| `WHATSAPP_SENDER` | sending number or instance id, if the gateway needs one |
| `WHATSAPP_AUTH_HEADER` | header carrying the key (default `Authorization`) |
| `WHATSAPP_AUTH_SCHEME` | prefix for the key (default `Bearer`; set empty for a raw key) |
| `WHATSAPP_TO_FIELD` | recipient field name (default `to`) |
| `WHATSAPP_MESSAGE_FIELD` | body field name (default `message`) |
| `WHATSAPP_SENDER_FIELD` | sender field name (default `from`) |

The field names are configurable because gateway payloads differ. The request
sent is:

```
POST $WHATSAPP_API_URL
Authorization: Bearer $WHATSAPP_API_KEY
Content-Type: application/json

{ "to": "919000000104", "message": "..." }
```

Numbers are reduced to digits before sending, so `+91 90000 00104` and
`919000000104` both work. Recipients come from `users.phone` and
`clients.contact_phone`.

### Proving it works

```bash
# what is configured, and can SMTP actually be reached
curl https://<api>/api/v1/notifications/channels -H "Authorization: Bearer $TOKEN"

# send a real message to yourself on either channel
curl -X POST https://<api>/api/v1/notifications/test \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"email":"you@yourfirm.com","phone":"+919000000104"}'
```

`POST /api/v1/notifications/:id/resend` retries one alert. The Automations page
shows channel state and a per-alert delivery breakdown.

## Receipt reading (auto-docket)

`POST /api/v1/receipts/auto-docket` accepts `file`, `rawText`, or `sampleId`.

| Input | Result |
|---|---|
| text-based PDF | text extracted with `pdf-parse`, fields matched |
| `.txt` | read directly |
| scanned image | `422 RECEIPT_UNREADABLE` — no OCR engine is installed |
| PDF with no text layer | `422` — it is a scan |
| unmatched text | `422` unless an application number, CBR number or title is found |

This is field extraction over text, **not OCR**. Scanned paper receipts need an
OCR engine (Tesseract or a cloud OCR API), which is not installed — it would not
fit in a 512 MB free instance.
